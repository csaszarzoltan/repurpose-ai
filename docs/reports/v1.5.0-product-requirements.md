# RepurposeAI v1.5.0 Product and UX Requirements

## Confirmed observations
- Archive was intentionally non-destructive, but archived projects were hidden from the browser workspace with no recovery path.
- Users could archive a project in one click without an explicit confirmation.
- Existing variants remained in storage after archive, so a restore workflow could preserve all prior work without schema changes.

## Requirements implemented

### Must have
- **UR-150:** Users can intentionally show archived projects from the primary workspace.
- **UR-151:** Users can restore an archived project without losing its variants or history.
- **FR-150:** Restoration changes only project lifecycle status from `archived` to `draft`.
- **FR-151:** The restore API is owner scoped and idempotent for a non-archived project.
- **UX-150:** Archive requires confirmation and explains that recovery remains possible.
- **UX-151:** Archived project cards expose only safe actions relevant to archived state.
- **A11Y-150:** The archive filter and restore action use labeled native controls and existing live-status feedback.
- **REL-150:** Archive and restore preserve immutable variants, recipes, and source data.
- **SEC-150:** Restore uses the same production authentication and tenant isolation as project reads and updates.
- **TEST-150:** Acceptance tests prove restore persistence and UI discoverability.

### Should have
- **AN-150:** Restore records only a content-free `project_updated` event with action `restore`.
- **UX-152:** Search and archived filtering can be combined in one bounded request.
